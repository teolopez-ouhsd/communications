Design System v1.0

One look and one set of rules for every OUHSD web app

This page is the reference for anyone building a web application for Oxnard Union High School District. Every example below is live, built from the same stylesheet your project will use, and every code block is copy-ready.

Start building Read the team guide DESIGN.md for AI tools
What changed from the earlier style guide Blue now leads and red is reserved for the one action that needs attention. Corners are nearly square. Labels sit above fields instead of floating. Tabs, accordions, and chips are keyboard accessible. Every class now starts with ou- and every value comes from a design token.

Quick start

Three steps. A team member or an AI assistant can finish them in a few minutes.

  1. Link the stylesheetOne file holds tokens, icons, and every component. Add it to the page head, with the two district fonts.
  2. Give AI the rulesCopy DESIGN.md into your project. It tells any AI assistant exactly which classes and tokens to use.
  3. Start from a templatePick the closest page template (login, dashboard, form, or list) and change the content, not the styling.

Principles

When a situation is not covered by a component or rule, decide by these six ideas.

Blue leads, red asks

Oxnard Blue is the strongest presence on every screen. Oxnard Red is a powerful accent, used once to draw attention or request action.

Quiet surfaces

Soft neutrals let the brand colors work as accents. If a screen feels loud, remove color before adding any.

Hard-edged and plain

Corners are only very slightly rounded. Shadows are subtle. Nothing bounces, glows, or decorates without a job to do.

Accessible by default

Every component meets WCAG 2.1 AA. Using the system as written is how a team stays compliant.

Ready for two languages

Families use these tools in English and Spanish. Layouts must survive text that is 30 percent longer.

Built for handoff

Named tokens, plain class names, and written rules mean a team or an AI can follow the system without asking.

Foundations

Color

Colors have jobs, not names. Use the semantic token (--ou-color-brand), never the raw palette value (--ou-blue-500), so a theme or a future update changes everything at once. Contrast ratios below are calculated live from the real token values.

Roles

Approved text and background pairings

Normal text needs 4.5:1 or better. Large text (24px, or 19px bold) and interface boundaries need 3:1 or better.

Contrast ratios for approved color pairings
PairingText tokenBackground tokenRatioResult

Use

  • Blue for navigation, links, selected states, and the default button.
  • Red for the single most important action or alert-level attention on a screen.
  • Container tints (-container) behind dark text for soft emphasis.
  • An icon and words with every status color.

Avoid

  • Red placed directly on blue, or blue directly on red. This is a brand rule.
  • Color as the only signal. About 1 in 12 boys and 1 in 200 girls have a color vision difference.
  • Hard-coded hex values. If a color is missing, ask for a token.
  • Gradients, glows, or one-off hues, including on school apps.

Foundations

Typography

Montserrat carries headings, buttons, and labels. Open Sans carries body text and form input. Body text never goes below 16px. Headings balance their own line breaks and paragraphs avoid single-word last lines, so text wrapping stays tidy without manual line breaks.

Heading hierarchy

Use real heading tags in order. One h1 per page, then h2, h3, never skipping a level for looks. Visual size follows the tag.

Foundations

Spacing and shape

Spacing runs on a 4px base. Pick a step from the scale instead of typing a pixel value. Corners are hard-edged and only very slightly rounded: 2 to 4 pixels. Fully round shapes are limited to avatars, radio buttons, and spinners.

Elevation and motion

Surfaces are flat by default and use a hairline border. Shadow appears only to show that something floats above the page or responds to a pointer.

Motion

Motion explains a change; it never decorates. Use --ou-duration-fast (120ms) for hover, --ou-duration-base (200ms) for opening and closing, and --ou-duration-slow (320ms) for large moves. All motion switches off for people who set "reduce motion" in their device.

Foundations

Icons

Icons are built into the stylesheet as CSS masks, so they take the color of their text and work on any domain with no extra files. Choose an icon to copy its markup. Decorative icons get aria-hidden="true". An icon-only button needs an aria-label.

Components

Buttons

Use a <button> for actions that change something on the page, and an <a> styled as a button for moving to another page. Labels start with a verb: "Save changes", "Send message", "Enroll student".

Emphasis levels

Use

  • Primary (blue) for the main action on most screens.
  • Action (red) for the one step that needs attention, such as Submit or Pay. One per screen.
  • Tonal or outline for secondary actions; text for Cancel and low-priority links.

Avoid

  • Two red buttons on one screen. If everything is urgent, nothing is.
  • A red button on a blue band. Use the inverse buttons there.
  • Vague labels such as "Submit", "OK", or "Click here".

Sizes, icons, and states

Hover and keyboard focus are live: press Tab to see the focus ring. A disabled button hides its reason from many users, so prefer leaving the button enabled and showing a clear message when something is missing.

Components

Forms

Labels always sit above the field and stay visible. Placeholders are for examples only, never for labels. Mark optional fields instead of required ones, since most fields are required.

Text inputs

Error state

Say what went wrong and how to fix it, next to the field, with an icon and words. Set aria-invalid="true" and link the message with aria-describedby. Keep what the person typed.

Choices

Use

  • The right input type (email, tel, date) and an autocomplete value.
  • One column on phones. Two columns only for short related fields.
  • A summary alert at the top for long forms, linking to each problem.

Avoid

  • Floating labels and placeholder-as-label. They disappear while people type.
  • Clearing a field after an error.
  • Red outline alone as the error signal. Always add the message.

Components

Feedback

Tell people what happened. Alerts sit in the page. Toasts confirm a quick action and then leave. Use role="alert" only for urgent errors, and role="status" for everything else.

Components

Badges and chips

Badges label a status or category and cannot be pressed. Chips are buttons that filter a list; they announce their on or off state to screen readers with aria-pressed.

Components

Cards

A card groups one idea. Whole-card links use a single real link inside the title, stretched over the card, so keyboard and screen reader users meet one link, not a block of text. Use filled cards rarely; they win attention by costing it everywhere else.

Components

Tables

Use a table only for data that compares across rows and columns. Give it a caption, mark header cells with scope, and wrap it in .ou-table-wrap so wide tables scroll instead of breaking the page. On phones, add ou-table--stack and a data-label on each cell to turn rows into readable cards.

Sorting is up to the app. The system styles the arrows from aria-sort on the column header; your code sets that attribute to ascending, descending, or removes it.

Components

Tabs

Tabs switch between views of related content on one page. Arrow keys move between tabs, and Home and End jump to the first and last. Do not use tabs for site navigation; use the navigation bar.

Components

Accordion

Built on the native <details> element, so it works with the keyboard, remembers nothing it should not, and needs no JavaScript. Give items the same name to open one at a time. Best for FAQs where most people need one answer.

Components

Dialog

A dialog interrupts the page, so use it only when a decision cannot wait: confirming a destructive action, or a short task that must finish first. It uses the native <dialog> element, which traps focus, closes on Escape, and returns focus to the button that opened it.

Name the buttons for what they do ("Delete record", "Keep record") instead of "Yes" and "No".

Components

Navigation

The header is white so the full-color logo always sits on a light background. A 4px stripe across the top carries the district blue, or a school's colors when a theme is applied. Include a skip link as the very first element on every page.

Build

School themes

A school-specific app keeps the district system and swaps only the school accent: add one stylesheet and one attribute. The header stripe, accent cards, and school badges pick up the school colors. Action red, link blue, focus rings, and status colors never change, so every app behaves the same way.

Three themes ship in v1: Pacifica, Del Sol, and Channel Islands. To add a school, copy themes/_template.css, fill in the colors from that school's brand guide, and check the contrast rules listed in the file.

Guidance

Content and language

Good interface writing is short, specific, and kind. These rules apply to every label, message, and button.

Write like this

  • Plain words at about an 8th-grade reading level. Say "use", not "utilize".
  • Buttons start with a verb and name the result: "Send message".
  • Errors say what happened and how to fix it: "Enter all 10 digits."
  • Sentence case everywhere. Capitalize only names and the first word.
  • Speak to the person: "Your request was sent."

Not like this

  • Jargon and acronyms without explanation.
  • Blame: "You entered an invalid value."
  • Exclamation points, except for rare celebrations.
  • Text inside images. It cannot be translated or read aloud.
  • "Click here" as link text.

English and Spanish

  • Build every screen to work in both languages from day one. Put the lang attribute on the page, and on any phrase in the other language.
  • Allow about 30 percent more room for Spanish. Never fix a button or label to its English width, and never cut text off with an ellipsis.
  • District and school names are never translated. Write "Oxnard Union High School District" and "Pacifica High School" in both languages.
  • The general term "high school" becomes preparatoria, not "secundaria".
  • Enrolling a student is inscribir (inscripción). Signing up for classes is registrarse (registro de clases). Keep the two ideas apart.
  • Have a fluent Spanish speaker review the final copy. Machine translation is a draft, not a finish.

Guidance

Accessibility

District web applications must meet WCAG 2.1 Level AA. The components already do the hard parts; your job is to use them as written and run these checks before launch.

Accessibility checks
CheckHow to test
Keyboard onlyPut the mouse away. Tab through the page. Every control works, the order makes sense, and the focus ring is always visible.
Zoom and reflowZoom the browser to 200 percent and resize to 360px wide. Nothing is cut off and nothing scrolls sideways except data tables.
Headings and landmarksOne h1, levels in order, one main, a skip link first, navigation labeled.
Labels and errorsEvery field has a visible label. Every error is in words, next to the field, and tied to it with aria-describedby.
ImagesMeaningful images have alt text that says what they show. Decorative images use alt="".
Screen readerComplete the main task with VoiceOver (Mac, iPhone) or NVDA (Windows) with your screen off.
Automated scanRun axe DevTools or Lighthouse. Fix every issue it reports. A clean scan catches about a third of problems, so it supports the manual checks and never replaces them.

Governance

The system works only if everyone uses the same one. These lightweight rules keep it stable without needing Communications in every project.

Ready to ship checklist

The team lead confirms each item before a new app goes live.

Versions and changes

  • Patch (1.0.1): fixes that change nothing visible. Teams get them automatically.
  • Minor (1.1.0): new components or tokens. Existing apps are unaffected.
  • Major (2.0.0): anything that changes how existing markup looks. Published at a new v2 URL; teams move when ready.

Need something the system lacks? Ask Communications and Marketing before building a one-off. If the need is real, it becomes a component for everyone.

Planned for v1.1

Dropdown menu, combobox, date picker, stepper, tooltip, selectable data table, and an optional dark mode. Until then, use the closest existing component and ask before inventing a new one.
